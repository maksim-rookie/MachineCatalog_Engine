# SQL-пайплайн: проект контрактов v1

Статус: проект для согласования, SQL в среде не применён.
Схема: ../../sql/001_catalog_schema.sql. Целевая СУБД PostgreSQL 15+.
Python 3.15 — целевая версия, совместимость зависимостей ещё не подтверждена.
Существующее окружение не изменяется.

## Этапы и границы

1. RegisterDocument -> DocumentRef: SHA-256 байтов, media_type, source_uri,
   original_name. Оригинал неизменяем; одинаковые байты имеют несколько sources.
2. DetectLayout(DocumentRef) -> PageLayout[]: page, dimensions, text availability,
   table/cell bounds. Нет нормализации значений и выбора модели.
3. ExtractCells(PageLayout, OCRPolicy) -> RawCell[]: document SHA, page, bbox,
   labels, raw value/unit, method, OCR audit. OCR отключаем и версионируем.
4. Normalize(RawCell, FieldDescriptor) -> MeasurementCandidate[]: source_fact_key,
   parameter/schema version, typed value, canonical unit, axis, conditions,
   extraction status, evidence, issues. Неоднозначность не разрешается догадкой.
5. ResolveIdentity(candidates, identity rules) -> VariantProposal[]: производитель,
   модель, комплектация, ссылки на документы. Совпадение названий не равно слиянию.
6. Validate -> ValidatedBatch: кандидаты, нарушения, метрики, версии контрактов.
7. Load(ValidatedBatch) -> LoadReceipt: транзакционный upsert, IDs, counts, state.
8. Match(TechnicalSpecification) -> MatchResult[]: подходит / не подходит /
   недостаточно данных, объяснение по каждому требованию и ссылки на evidence.

Каждый конверт содержит contract_version, document_sha256, run_key, stage,
engine_version, config_sha256, ocr_config_sha256 и payload.
Размеры bbox — PDF points, начало координат сверху слева; OCR переводит координаты
из пикселей обратно в PDF points. Точность OCR не означает правильность измерения.

## Дескриптор поля

Пример: config/field_descriptor.example.json. Старые rule.key становятся id;
правила регулярных выражений остаются в extractor_hint. Новая версия определения
не изменяет исторические записи. required задаётся профилем класса/варианта.
Единицы задаются реестром размерностей; несовместимая конвертация запрещена.
Составные XYZ значения раскладываются на отдельные осевые измерения только при
подтверждённом порядке. Объединённая ячейка — проекция для пользователя.

## Контракт загрузки и идемпотентность

- Ключ обработки: document SHA + engine version + config hash + OCR config hash.
- source_fact_key детерминирован из source row/cell, параметра, оси и условия;
  он не строится из отображаемой строки. Альтернативы имеют разные ключи.
- Сначала staging и проверки ссылок/типов; затем одна транзакция на документ.
- В одной транзакции фиксируются измерения, evidence, issues и завершение run.
- Повторный запрос для завершённого run возвращает существующий LoadReceipt.
  Частично загруженные данные не видны подбору. Повторная попытка того же run
  выполняет upsert по (run_id, source_fact_key), не дублирует evidence/issues.
- Конкурирующие загрузчики сериализуются блокировкой строки processing_runs.
- Новая версия извлечения создаёт новый run, не переписывает прошлые факты.
- Дополнительные проверки загрузчика: evidence относится к документу run;
  variant связан с тем же документом; единица совместима с descriptor;
  numeric конечен; bbox числовой и в пределах страницы. Эти межтабличные
  ограничения не выражены полностью в начальном DDL.
- Для актуального поиска выбирается явно назначенная версия данных документа;
  все исторические processing_runs одновременно в поиск не включаются.

## Подбор

Требование: parameter_id, operator, value/range, unit, axis, mandatory,
verification policy. Сначала нормализация единиц, затем индексируемый отбор.
Для минимального требования >= T: скаляр должен быть >= T. Диапазон трактуется
по семантике параметра (рабочий диапазон / возможная комплектация / погрешность),
а не автоматически по верхней границе. Без этой семантики — insufficient_data.
Нет значения, конфликт, неподтверждённая идентичность или отсутствие разрешённого
статуса достоверности -> insufficient_data. Подтверждённое нарушение -> fail.
Все обязательные требования pass -> pass; веса предпочтений ранжируют только
после обязательного отбора. Возвращаются значения, правила сравнения и provenance.
Начальная SQL-схема даёт индексы, но не реализует сам сервис подбора.

## Совместимость и перенос

1. Зафиксировать эталонные артефакты и измеримые расхождения.
2. Преобразовать текущий facts JSON в staging без потери value_raw и source.
3. Параллельно сравнить SQL-проекции с текущими результатами.
4. Оставить legacy-export адаптер со старыми именами/полями минимум на релиз.
5. Включать SQL как основное хранилище после проверки импорта и восстановления.

Текущая JSON-only рабочая редакция пока не удовлетворяет legacy-контракту:
адаптер обратной совместимости необходимо реализовать до переходного выпуска.
Старые кэши не перезаписываются. SQL-миграции версионируются отдельно от схемы
параметров. Удаление исходных каталогов и автоматическое слияние моделей запрещены.

## Приоритеты

P0: проверить Python 3.15/Windows wheels, согласовать descriptor и SQL-ограничения,
зафиксировать golden baseline, определить актуальную версию документа и политику
достоверности для поиска. Риск: зависимости и семантика идентичности.
P1: staging/loader, миграции, проверка повторной и конкурентной загрузки,
legacy-export, поиск с трёхзначным результатом. Риск: дубли и ложное соответствие.
P2: очереди OCR, потоковая загрузка, поисковые проекции и нагрузочные испытания.
Сроки оцениваются после P0 и получения исходных PDF; производительность не измерена.

Критерии приёмки: повторная загрузка не меняет число фактов; отказ откатывает
документ; конфликт не попадает в подтверждённый подбор; нули не становятся NULL;
источник восстанавливается для каждого результата; старый экспорт воспроизводим;
backup/restore и миграции проверены на тестовой PostgreSQL. Покрытие и Python 3.15
не объявляются подтверждёнными без отдельного выполнения проверок.
